01 / 使用场景

举个例子

你做了一个每天帮你整理资料的 Agent。

它需要反复调用模型。你希望它找到可用的接口、比较报价，还得控制一天花多少钱。另一边，有人运行着模型节点，愿意把空闲容量挂出来卖。

TAM 让卖家发布服务，买方网关从同模型、同结算币的卖家里选择。每次调用前锁价，收到完整回答后按报告用量签账单。下面的演示就从这笔调用开始。

01

换一家卖家，又要重新接接口？

卖家发布模型和报价。买家通过兼容 API 接入，网关负责发现、比较和选择可用节点。

02

闲的时候想接单，忙的时候顾不过来。

卖家设底价和调价规则，AIMM 跟着容量占用调整报价，也可以一直用固定价。

03

回答传到一半断了，这钱付不付？

买方先检查回答是否完整、非空和未超预算。检查失败，就不签最终付款账单。

卖家发布服务。引导与中继帮助发现和连接，买方网关比较同模型、同结算币的报价与可用状态，选择卖家。

先存一笔预算，每次调用前再定上限。

买家把结算币存进托管合约。调用前锁价，签一份限定本次最高费用的预算意向；这份意向在链下签署，不能直接拿去收款。

问题发给卖家，卖家调用模型。

请求正文在买卖网关之间加密传输。卖家使用自己接入的模型服务生成回答，上游密钥保留在卖家端。

回答逐段回来，买方检查是否收全。

完整、非空且报告用量未超预算，才进入付款确认。断流或检查失败，不签最终付款账单；完整收到不代表答案一定正确。

收到完整回答，再签实际费用。

买方按锁定价格和报告用量计算费用，在你授权的规则内签付款账单。这一步不上链，不为每次调用单独付 Gas。

账单攒成一批，再上链收款。

卖家保存签名账单，批量提交给合约。合约逐张核验、阻止重复收款，再从买家的托管预算支付。充值、收款和退回预算仍需 Gas。

网站展示卖家和报价；买方网关自己选路、签名。引导与中继帮助连接，不统一分派订单。

03 / 关键机制

01 / AIMM 动态定价

卖家设底价，程序按忙闲报价。

容量占用上升时自动涨价，空闲时回到底价。每次调用先锁价，回答生成到一半不会临时加价。卖家也可以选择固定价。

签名报价调用前锁价
02 / 链下签名与批量结算

先批预算，收到完整回答再批付款。

预算存进链上合约，单次意向和付款账单在链下签署。卖家攒多笔账单再收款，减少逐笔上链的开销。

批量示意；实际 Gas 取决于批次大小和网络费用。

03 / 去中心化节点

买方自己比价、选卖家。

服务和报价通过 P2P 网络传播。买方网关决定连接哪个卖家，没有中心调度服务器替它分派订单。引导和中继负责帮助连接。

公开报价买方自主选路

AIMM / 拖动看看

占用一半容量时，会报什么价？

下面用 5 USDC 的底价举例。调价力度为 1、容量占用 50% 时，报价是 10 USDC／百万 Token。

P = P₀ ÷ (1 − u)α
P₀：底价u：容量占用α：调价力度
占用怎么算？输入输出价格怎么变？

有上游配额跟踪时，用配额使用比例；否则用处理中的请求数除以最大并发数。不是 CPU 使用率。

输入和输出费率按同一倍数调整；BEM 使用相同公式，单位换成 BEM。卖家可以设置最高价。

使用前需要知道的几件事

目前模型来源和用量仍由卖家声明，真实 zkTLS 验证尚未接入。完整收到回答不证明答案正确。当前内测由卖家审核买家，公开交易争议机制仍待完善。

引导、中继、网站和上游模型仍有服务器组件。买方自主选路和授权付款，并没有把大模型变成完全去中心化计算。

BEM 与 USDC 分别报价结算，不会自动兑换。测试币不代表真实资产，主网尚未启用。
